# Architecture

Living document. Update it in the same change whenever a component, data model, boundary or decision changes. Last major revision: 2026-11-10 (inbound webhook monitoring, incl. AWS Lambda); v1 built 2026-11-04, plan from 2026-11-03.

## 1. Product in one paragraph

Theirside tells a team, within minutes, when a specific third-party provider endpoint starts failing, e.g. "Acme Cards `POST /v2/cards/:id/activate` failing 38% for 6 min (normally 0.2%), other Acme endpoints OK". A drop-in SDK records outgoing HTTP calls. A collector stores them, learns a baseline per endpoint, scores health and alerts. It also watches the webhooks providers send the app (silence against the learned hour-of-week rate, rejections, slow handling, delivery lag). Outputs are a developer dashboard, a health API and an embeddable status page the customer shows its own clients. Out of scope: monitoring the host app itself (Sentry does that).

## 2. Editions and licensing

### 3.1 SDK (`packages/sdk`)
- `init(config)` instruments `fetch`/undici via `diagnostics_channel`, Node `http`/`https` via `http.client.*` channels where available or wrapping `request`/`get` otherwise. Axios is covered through those. One call is counted once.
  - undici: `undici:request:create` / `:headers` / `:error`. Request headers are a string on Node 18 and an array later; response headers are an array of Buffers on all supported versions.
  - http/https: `http.client.request.start` fires with the `ClientRequest` on every supported version (verified 18.18.0, 18.20, 20.9, 20.20, 22, 24). `http.client.request.error` is missing on 18 and early 20, and no channel reports client-side timeouts or caller aborts, so on all versions the outcome comes from observing that request's own events by wrapping its `emit` (no listeners are added, so the host app's error semantics don't change). Node < 18.18 or runtimes without the channel fall back to wrapping `http(s).request/get`.
  - A call is recorded at response headers (status, time to headers) or at a failure before them. Each `ClientRequest` is tagged with a symbol so wrappers stacked by X-Ray/OTel/nock never cause a double count.
  - Channels are subscribed once per process and never unsubscribed; module-level dispatchers forward to the active client (works around a Node 18.18 bug where a channel that lost its last subscriber never delivers again).
- Must coexist with AWS X-Ray `captureHTTPsGlobal`, Sentry/OpenTelemetry http instrumentation and `nock`.
- Two builds, one API (`src/api.ts` over a `Runtime`): the Node entry (`src/index.ts`: capture as above, uploads through `http.ClientRequest` on its own agent) and a fetch-only entry (`src/edge.ts`, `@theirside/sdk/edge`) for Cloudflare Workers, Deno, Bun and Vercel/Netlify Edge, picked by conditional exports (`workerd`, `worker`, `deno`, `bun`, `edge-light`). The fetch build wraps `globalThis.fetch` (records at response headers or on error, returns and rethrows unchanged), uploads with the fetch it found before wrapping (gzip via `CompressionStream`), imports no Node module (built with platform `neutral`; CI checks it on Bun and in workerd via Miniflare) and on Workers uses no timers: events go out and the remote config is refreshed in `flush()`.
- Pooled learning (SDK 0.2.0 + collector 0.3.0, `modules/discovery/pooled-learning.ts`): learning state is per (project, service, environment), never per instance. The SDK asks for the remote config with `?service=&environment=`; the collector counts distinct literal words per provider + parent template + position over the service's templates of the last 7 days (versions and Cloud Endpoints words excluded) and returns the positions past 16 as `learned: [{provider, hosts, parent, position}]` (cached 5 minutes per service, at most 2,000). The SDK marks each under the key its learner uses for those hosts, so a cold start behaves like a warm instance once the fetch lands; the fetch never blocks startup. Balanced mode's 5-sightings count stays per process (pooling it would need the words or their hashes). Endpoint merges and merged routes stay project-wide, as before.
- Short-lived processes: `flush(timeoutMs)` sends everything queued and resolves within the timeout whatever the collector does; `wrap(handler, { flushTimeoutMs = 300 })` always flushes after the handler (capped on AWS Lambda by `getRemainingTimeInMillis()` − 50 ms; `flushTimeoutMs: 0` skips it unless the invocation was a webhook delivery, which is recorded only when the handler returns, then capped at 300 ms) and returns or rethrows unchanged; `wrapFetch` hands the flush to `waitUntil` so the response isn't delayed. Serverless mode (`serverless`, detected from AWS Lambda, Google Cloud Functions, Azure Functions, Vercel, Netlify, Deno Deploy and Workers environment variables) means no exit hooks, no heartbeat, no keep-alive sockets (a frozen process leaves stale ones), and the function name as the default `service`.
- Auto-discovery (default `autoDiscover: true`; `trackUnknownHosts` is a deprecated alias): every third-party host is recorded with `provider: null` except loopback, private/link-local ranges, cloud metadata, internal names, telemetry hosts, the collector, `OTEL_EXPORTER_OTLP_*`/`SENTRY_DSN` hosts, `internalHosts` and hosts hidden or marked internal in the dashboard (`packages/shared/src/exclusions.ts`, `packages/sdk/src/discovery.ts`). Listed `providers` keep their name and routes. `autoDiscover: false` = listed providers only.
- Inbound webhooks (SDK 0.3.0, `src/instrument/server.ts`, `src/inbound.ts`; detection table `packages/shared/src/webhooks.ts`): `http.server.request.start` / `http.server.response.finish`, subscribed once like the client channels. At start only header *presence* is checked against the sender rules (a combination per sender, never one shared header: GitHub by `x-github-event`, GitLab before the Standard Webhooks headers it also sends), plus declared `webhooks: [{ path, provider }]` routes (they win; needed for Adyen/Mailgun, and to name Svix customers); anything else returns at once. The one header value read is the sender's timestamp (≤ 512 characters, number only). Pending deliveries live in a `WeakMap` keyed by the response; `close` before `finish` (observed through the response's `emit`, no listener) is status null, outcome `timeout`. Route templates use the outgoing templater with strict path privacy and webhook words plus sender names as allowed words (key `@inbound`, 100 templates). Never sampled. Collector support (`InboundSupport`: unknown, yes, no): deliveries reach the main queue only once the remote config says `inbound: true`; before that the first 500 are held for at most 60 s and moved into the queue on yes, discarded on no (a config without it, or 404) or when no answer comes. With `inbound: true` in `init()` (Lambda cold starts) there is no time limit: held deliveries (≤ 500 between flushes) go out at each flush in batches of their own to `POST /v1/ingest/inbound` (`Transport.sendProbe`); 2xx means yes, 404/405 means no (held and queued inbound events dropped, recording off), other errors keep them for the next flush with the usual backoff. `webhooks: false` subscribes nothing.
- Webhook discovery (SDK 0.3.0, widened in SDK 0.4.0; `classifyWebhookCandidate` in `packages/shared/src/webhooks.ts`, `InboundRecorder.candidate`): a POST/PUT that no sender rule or declared/confirmed route claims is a *candidate* when it has no browser header (`cookie`, `origin`, `referer`, `sec-fetch-*`, `x-requested-with`, CSRF headers) and any of: a route word as a whole segment (`webhook(s)`, `hook(s)`, `callback(s)` anywhere; `notify`, `notifications`, `events` only last or before one final plain name, and without `authorization`/`x-api-key`), a header name containing `signature` or `hmac`, CloudEvents (binary `ce-specversion` + `ce-source`/`ce-type`, or `content-type: application/cloudevents+json`), or a `Host` whose first label contains `hook`/`callback`. Header values read: `host`, `content-type`, `ce-source`, `ce-time` only (`CANDIDATE_VALUE_HEADERS`). One function decides for every entry path; the Lambda adapter (`lambda.ts`) only normalises its event into the same view (headers case-folded, payload 2.0's `cookies` reported as a `cookie` header). Its own templater (key `@candidate`, 50 routes, strict privacy); the suggested name comes from `ce-source`'s domain, else a digit-free plain word next to a route word, else the last segment after a version segment; that path segment (lower-case as sent) is kept literal in the route whichever rule names the sender; 16 such words per process (path segments and names together); sent as `provider`, else `unknown`. A confirmed or declared route with CloudEvents headers takes its send time from `ce-time`. `THEIRSIDE_DEBUG=inbound` or `debug: 'inbound'` logs each incoming request's decision and the rule behind it (`InboundRecorder.trace`; names only, IDs as `:id`), and one line per flush (`Client.inboundFlushLine`: deliveries and candidates per POST, route, status; else held / timeout); `getStats().inbound` counts held, sent, dropped and candidates. One event per route a minute with `candidate: true` and `count` (deliveries since the last), 50 routes per process. Same collector-support handling as deliveries. The remote config's `webhookRoutes` (confirmed) are added after the declared routes; `ignoredWebhookRoutes` are dropped after templating. `webhookDiscovery: false` turns it off.
- AWS Lambda webhooks (SDK 0.3.0, `src/lambda.ts`): `wrap()` passes each invocation's event to `Client.lambdaBegin`; API Gateway REST (payload 1.0: `httpMethod`, `path`), HTTP API and function URLs (payload 2.0: `requestContext.http.method`, `rawPath` with a named stage stripped; a `.lambda-url.` domain is a function URL) and ALB (`requestContext.elb`) give method, path and header names from `headers`/`multiValueHeaders` (lower-cased index of names, a value read only for the sender's timestamp), and go through the same `InboundRecorder.begin`. Other events have no such shape and are ignored. The status is the one the sender got (`lambdaStatus`): `statusCode`; otherwise 200 for payload 2.0 and 502 for REST/ALB; a throw is 500 (payload 2.0) or 502 (REST/ALB). Duration is the handler's run, recorded before the flush. Works in either build, since it reads only the event; other serverless runtimes record no incoming requests.
- `untracked(fn)` (`src/untracked.ts`): an `AsyncLocalStorage` scope checked in `Recorder.begin`, the single entry for http and undici capture, so calls started inside `fn` or async work it spawns are never recorded; `track()` is explicit and still records. For user-supplied URLs (image downloads, customer webhooks) that aren't providers.
- Route learner (`RouteLearner` in `templating.ts`): per host + parent template + position, sightings per literal value as 32-bit hashes with counters. Path privacy (`pathPrivacy`, per call via `PathPolicy`): `strict` (default) sends a literal only when every word of it (`pathWords`: separators and camelCase) is in the vocabulary (`vocabulary.ts`, generated by `tools/vocabulary`) or the provider's allowed words; strict sends such a literal from the first sighting. `balanced` skips the vocabulary check and sends a literal only from its 5th sighting (`:id` before; results with a provisional `:id` aren't cached). In both, version segments are exempt and > 16 distinct values → `:id`. Slots are keyed by provider (`PathPolicy.key` = `@p:<name>`) when the SDK knows the host's provider (init() or a remote-config provider), else by host. The mode per provider is the dashboard's (remote config `providers[].pathPrivacy`) when set, else init()'s; `providers[].allowedWords` adds words. Explicit routes (init, dashboard, catalog `routes`) bypass it. Tenant-style subdomains share one key `*.domain`: after 20 distinct subdomains of a domain (`TENANT_FOLD_SUBDOMAINS`, the collector's fold threshold; domain = host minus its first label, no PSL in the SDK), or at once for the remote config's `tenants`. Capped at 500 slots × 17 counters + 2000 learned positions + 1000 domains × 20 label hashes + 1000 folded domains, all with least-used eviction (lowest tenth dropped when full, counts halve every `max` inserts); cached templates count a use on their slots so busy paths stay. The templater's per-host sets are capped at 500 hosts (LRU).
- Remote config: `GET /v1/sdk-config` (ingest or read key) every 60 s with ETag, in the background; failures keep the last good config. Carries hidden/internal host patterns, routes per provider (the project's, then catalog `routes` for every catalog provider that ships them), per-provider `pathPrivacy` (dashboard) and `allowedWords` (dashboard, then catalog `allowedWords`); a provider is sent when it has any of these, or (within a 256 KiB budget) when it has more than one host or pattern, so the SDK can key its learner by provider, `tenants` (the `*.domain` patterns the directory folded, for the route learner; absent from older collectors), sampling (`packages/shared/src/sdk-config.ts`). Precedence: hidden/internal always apply; `init()` routes first, then remote routes. A 404 (collector without the endpoint) switches auto-discovery off for the process (see §4 protocol).
- Ring buffer (`maxQueue`, drop oldest), flush on interval or batch size, unref'd timers, backoff up to 60 s, one batch in retry. Uses un-instrumented transport so it never records itself: the original `http.ClientRequest` captured at module load plus a dedicated agent, which also keeps the uploads out of X-Ray/OTel traces. Sockets are unref'd except during `shutdown()`. Reports dropped-event counts and the last flush error.
- `shutdown()` flushes with a 2 s cap; also run on `beforeExit` and `SIGTERM` (one-shot listener; if no other SIGTERM listener exists the signal is re-raised after the flush so the default exit still happens).
- Never throws into user code; target overhead p99 < 0.1 ms per call (measured: `docs/benchmarks.md`).
- Zero runtime dependencies; `packages/shared/core` (no zod) is bundled in by tsup. CJS + ESM + d.ts, Node 18.18+.
- Identical for self-hosted and cloud: switching is `endpoint` + `apiKey`.

### 3.2 Shared (`packages/shared`)
- Event schema (TypeScript types + zod), ingest protocol version, outcome enum.
- Endpoint templating: explicit routes win; auto-collapse IDs (ints, UUID/ULID/ObjectId, long hex, token-like strings, prefixed IDs like `cus_123`, emails, any 12–19 digit run); strip query/fragment; 200 templates per host cap then `/:overflow`. Exact rules: `docs/privacy.md`.
- Latency histogram: 130 fixed buckets, upper bounds 2^(i/8) ms (≈ 9% steps) from 1 to 65 536 ms then +∞ (`LATENCY_BUCKET_UPPER_MS`); quantiles by log-linear interpolation inside a bucket; `countAbove` counts calls slower than a duration. Every eighth bound is a power of two, so the 18-bucket histogram of rows from before collector 0.4 maps onto groups of eight (`addCoarse`). Stored as one nullable column per bucket (NULL when empty). Changing the buckets is a breaking change for stored rollups.
- Two entry points: `@theirside/shared/core` (dependency-free: constants, outcomes, histogram, templating, host patterns, network row) and `@theirside/shared` (adds the zod schemas).
- Network aggregate row type (see 5.4), so the format is fixed early.

### 3.2a Design (`packages/design`)
- `tokens.json` is the only source of colours (dark and light themes, semantic names, chart series), fonts, type scale, spacing (4 px grid), radii, shadows, focus ring and control sizes. `themeCss()` turns it into CSS custom properties (`--color-*`, `--chart-*`, `--text-*`, `--space-*`, …): `auto` follows `prefers-color-scheme`, and `data-theme="light|dark"` on any element overrides it for that subtree. The build writes `dist/tokens.css` for the dashboard; the collector's status page calls `themeCss()` directly.
- Fonts are self-hosted (Albert Sans for UI, Roboto Mono for code and endpoints; OFL-1.1, Latin and Latin Extended, `fonts/`), so no UI makes third-party requests.
- Tests: WCAG contrast of every text/background token pair in both themes (≥ 4.5:1; focus ring ≥ 3:1). Usage rules: `docs/design-system.md`.

### 3.3 Collector (`apps/collector`)
- Fastify + `pg`. Config by env only (`apps/collector/src/config.ts`). Stateless HTTP layer; one scheduler leader via Postgres advisory lock, so it can run with several replicas.
- Modules: `ingest`, `storage` (repository interfaces + Postgres implementation), `scheduler`, `scoring` (incl. `inbound.ts`, `silence.ts`), `incidents` (incl. `inbound.ts`: the webhook engine, texts and job), `alerts` (channel adapters), `api` (incl. `webhooks.ts`), `status-page`, `auth`, `entitlements`, `usage`.
- Serves the dashboard SPA build (`apps/dashboard`, Vite + React + uPlot, hash routing, built into `apps/collector/public` and shipped in the image) at `/`. Auth pages: setup (first run), sign-in with the 2FA step and break-glass admin token, `#/invite/<token>`, `#/reset/<token>`, `#/forgot` (SMTP only), and a full-page 2FA enrolment when the org requires it; `#/account` (password, 2FA with QR code and recovery codes, sign out everywhere) and Settings → Users (invites with a role, role changes, reset links, sign-out, remove, turn off 2FA, require 2FA; changes to another user go through a step-up form). For members the dashboard hides the admin-only tabs (alert channels, API keys, status page, users) and controls (a provider's status page fields, the discovery digest); the collector enforces the same rules. Endpoint rows show the marks ("400 expected", Unmark), the share tagged in code, an "Expected answers" chart (per reason, and marked statuses dashed), "recovering · last bad minute N min ago" instead of the red badge while an incident's window is already healthy, and colour only the column the open incident is about (errors, 4xx, 429 or p95).
  - Dashboard pages for webhooks: `#/webhooks` (all providers) and a Webhooks card on each provider page (table, per-route charts, the expected-quiet box); Settings → Providers → a provider → Webhooks (overrides, "Also show its webhooks" under the status page); Settings → Thresholds → Webhooks.
  - Simulation mode only (`THEIRSIDE_SIM=1`, docs/demo.md "Simulate weeks in minutes"; every path a 404 otherwise; admins): `GET /__sim/clock`, `PUT /__sim/clock` (`{speed, paused}`), `POST /__sim/clock/advance` (`{minutes|hours|days}`: a jump, every minute in between at max speed, then back to paused or running; status `jumping`, `jumpTo` in the clock), `DELETE /__sim/clock/advance` (stop the jump where it is), `GET /__sim/state` (scenario, clock, timeline, expectations), `GET /__sim/reference` (every scenario setting with its summary and default, from `apps/collector/src/sim/reference.ts`: the page's field hints and Reference panel, `pnpm sim:help`, generated docs/simulation-reference.md), `GET /__sim/scenarios[/:name]`, `PUT /__sim/scenarios/:name` (save YAML), `POST /__sim/validate`, `POST /__sim/load` (`{name|yaml|scenario, history?}`: resets the simulation database), `PUT /__sim/scenario` (live edit, or the reason a restart is needed); `/v1/auth/status` carries `simulation`, and the dashboard shows the banner and the Simulation page (`#/simulation`).
  - Public: `GET /status/:token` (server-rendered HTML, `?theme=auto|light|dark`, `?providers=<display names>`, `?embed=1`; cached `THEIRSIDE_STATUS_CACHE_SECONDS`, default 30, in memory and via `Cache-Control`), `GET /embed.js` (inserts an auto-height iframe; `data-token`, `data-theme`, `data-providers`), `GET /fonts/:file` (the self-hosted UI fonts from `packages/design`, the files listed in `FONT_FILES` only). The page's colours, type and spacing come from the design tokens (`themeCss()`, §3.2a).
- Endpoint merges (`modules/discovery/endpoint-merge.ts`), "one call, one row": services learn path templates independently, so one call can arrive as several templates. Ingest collapses repeated slashes in every template (SDKs before 0.1.1 kept the empty segment of a base URL ending in `/`) and rewrites a provider's `endpoint_aliases`. An hourly job (templates of the last 7 days; the first run after an upgrade: all retained rollups) and every change that adds allowed path words (that provider, all history) merge per provider, method and segment count: a template with `//` into the collapsed one, and an `:id` template into the single most specific known template that has, where it has `:id`, one of the provider's allowed words (dashboard or catalog) or the Cloud Endpoints `_ah`/`api`, and is equal elsewhere. Never on general vocabulary words (`/users/:id` is not `/users/me`) and never when two templates fit equally (`/v1/:id` next to several methods). Each provider's merges are one transaction: rollups (all minutes, added into existing rows), raw events and incident endpoints (combined when one incident has both: earliest first seen, worst peak, recovered only if both were; one endpoint left makes it endpoint-scoped) move; the old template becomes an alias; merged templates without `:id` become routes (remote config). Both endpoints' baselines are dropped and recomputed from the merged history right after. Running it again changes nothing. SDK 0.1.0 rows whose `//` became `:id` are not merged (which `:id` was the slash can't be told); SDK 0.1.1 and later collapse repeated slashes themselves. Collector 0.2.2 also pushed doubled-slash routes for SDK 0.1.0; 0.3.0 no longer makes them and migration 011 removes them.
- Health computation (`modules/api/health.ts`) reuses the scoring code over the last complete 5-minute window and cached baselines; endpoints in an open (non-muted) incident are red. Endpoints come from the rollups of the requested range (one `aggregateByKey`, which also gives each key's last minute and range totals): with calls in the window they are scored, without they are `idle` (no score, live values 0/null, never green or red, `inIncident` still set). Providers come from the provider rows, so a known provider never drops off: no calls in the window and a `last_call_at` makes it `idle`, none ever makes it `unknown`; an open incident still makes it at least amber. Order: providers red, amber, green, idle, unknown; endpoints live by calls/min, then idle by last call. The status page shows idle as "no data". Status-page daily uptime = 1 − incident minutes / minutes in the day (more than 30 incident minutes = outage, otherwise degraded; no traffic and no incident = no data).
- Startup: wait for Postgres (up to ~2 min), apply `migrations/*.sql` in order (tiny runner, advisory-locked, `schema_migrations`), bootstrap, create today's partitions, listen, start the scheduler.
- `AppContext` (`context.ts`) carries config, storage, clock, entitlements resolver, API-key authenticator, sessions and usage limiter; tests build it with a fake clock, cloud can pass its own `EntitlementsResolver`.
- Health: `GET /healthz` liveness, always 200 with `db: ok|unavailable` (an orchestrator must not restart collectors during a DB outage); `GET /readyz` 503 while the DB is unreachable.
- Docker: `docker/Dockerfile.collector` (multi-stage, `pnpm deploy --prod`, runs as `node`, `HEALTHCHECK` on `/healthz`), `docker/compose.selfhost.yml` (the user-facing self-host file: postgres + the `ghcr.io/theirside/collector:0.6` image, project `theirside-selfhost`, optional SMTP; the single source of what theirside.dev serves as `/compose.yml`, which the website's own CI copies from the latest release; `docker/selfhost-quickstart.sh` runs the website's Quick start against it with a given image), `docker/docker-compose.yml` (the dev/demo file: postgres + collector, zero-config: no key or token required; `--profile demo` adds the demo stack, started with `--env-file docker/dev.env` for the well-known dev key and admin token its services share with the collector; `THEIRSIDE_VERSION` picks the released image, which is only pulled; `local`, the default, builds the checkout as `:local`). Releases: `.github/workflows/release-collector.yml` on a `v*.*.*` tag (or manual run with a version) runs the collector tests and the self-host Quick start (`selfhost-quickstart`, also a CI job on every push to main), then pushes `ghcr.io/theirside/collector` for linux/amd64 + arm64 tagged `<version>`, plus `<major>.<minor>` when it is the newest patch of that minor and `latest` when it is the newest stable version by git tags (never for prereleases); a manual run with `retag` only points those two at an already-published version, with OCI labels, BuildKit provenance + SBOM and a GitHub build provenance attestation.
- Key env vars: `DATABASE_URL` (required), `THEIRSIDE_DATABASE_CA_FILE` (PEM CAs the database certificate must chain to, `verify-full`; `storage/pg-connection.ts`; the image carries AWS's RDS bundle at `/app/certs/rds-global-bundle.pem`), `PORT` (4318), `THEIRSIDE_DEPLOYMENT_MODE`, `THEIRSIDE_PUBLIC_URL`, `THEIRSIDE_BOOTSTRAP_API_KEY` and `THEIRSIDE_ADMIN_TOKEN` (both optional; with neither, first run is zero-config, §4), `THEIRSIDE_BOOTSTRAP_ORG_NAME`, `THEIRSIDE_BOOTSTRAP_PROJECT_NAME`, `THEIRSIDE_LICENSE_KEY`, `THEIRSIDE_ALLOW_DEV_LICENSE`, `THEIRSIDE_RAW_RETENTION_DAYS` (30), `THEIRSIDE_ROLLUP_RETENTION_DAYS` (90), `THEIRSIDE_PARTITIONS_AHEAD_DAYS` (3), `THEIRSIDE_SCHEDULER_ENABLED`, `THEIRSIDE_SCHEDULER_INTERVAL_MS` (60000), `THEIRSIDE_SMTP_URL` or `THEIRSIDE_SMTP_HOST`/`_PORT`/`_SECURE`/`_REQUIRE_TLS`/`_USER`/`_PASS`/`_FROM`, `LOG_LEVEL`, `THEIRSIDE_SESSION_MAX_AGE_HOURS` (168), `THEIRSIDE_SESSION_IDLE_HOURS` (24), `THEIRSIDE_TRUST_PROXY` (private and loopback ranges; load-balancer CIDRs, a hop count, false, or true for any with a warning), `THEIRSIDE_SECRET_KEY` (≥ 32 characters; required for 2FA), `THEIRSIDE_SECRET_KEY_PREVIOUS` (comma-separated, for rotation), `THEIRSIDE_AUTH_PROXY` (off; header, alb), `THEIRSIDE_AUTH_PROXY_TRUSTED_IPS`, `THEIRSIDE_AUTH_PROXY_HEADER` (X-Forwarded-Email), `THEIRSIDE_AUTH_PROXY_ALB_ARN`, `THEIRSIDE_AUTH_PROXY_AUTO_CREATE` (false), `THEIRSIDE_ADMIN_EMAILS` (proxy-created accounts that become admins), `THEIRSIDE_STATUS_CACHE_SECONDS` (30), `THEIRSIDE_PUBLIC_PATHS_ONLY` (false: a public-facing instance serving only `/status/*`, `/embed.js`, `/healthz`, `/readyz`, without scheduler), `THEIRSIDE_CATALOG_OVERRIDE` (JSON file with extra catalog entries; demos and tests), `THEIRSIDE_DESIGN_GALLERY` (false; the dashboard's `#/design` page without sign-in, set by the compose stack).

### 3.4 Deployment modes
`THEIRSIDE_DEPLOYMENT_MODE=self_hosted | cloud`. The mode only changes defaults (bootstrap org/project from env, auth method, where entitlements come from). Feature checks never branch on mode; they ask entitlements.

## 4. Tenancy, auth, entitlements

- Hierarchy: `org` → `project` → `environment` (string on events, e.g. `production`). Every tenant-owned table has `org_id`, and `project_id` where relevant, from day one, even though self-hosted runs a single org.
- Users (free edition, `modules/auth`): built-in accounts in `users` + `memberships` (migration 005). SSO, custom roles and an audit log stay paid entitlement flags (`sso`, `rbac`, `auditLog`) and are not built.
  - Roles (migration 007, `memberships.role`): two fixed roles. **admin** may do everything. **member** may read everything (overview, providers, incidents and their summaries, SDK health, channel and key lists without secrets), manage providers (rename, hide/internal, alerts on/off, hosts and routes, merge, split, support contact, path privacy, allowed path words) and their own account and 2FA; not users, invites or roles, other users' 2FA or passwords, API keys, alert channels and thresholds, the new-provider digest, status pages (including a provider's `isPublic` and public name), security settings, or the licence (an env var). Enforced in the auth preHandler (`checkRole`): reads are open to members and writes need an admin unless the route says `config: { role }` (`member` for provider and own-account writes, `admin` for the users list and security settings), so a new write route is admin-only by default; refusals are 403 `admin_only` naming the area. `test/roles.test.ts` lists every route's role. The first user from setup is an admin, invites carry a role (`auth_tokens.role`, default member), proxy-created users are members unless their email is in `THEIRSIDE_ADMIN_EMAILS` (or, without that list, they are the very first user); an invite's role applies to proxy sign-in too. The last admin who can sign in can't be demoted or removed (409 `last_admin`; the admins' membership rows are locked `FOR UPDATE` during the check so two admins can't demote each other at once); the admin token is an admin but doesn't count. Role changes need step-up and email the user. Migration 007 made every existing user and pending invite an admin, since all could do everything before.
  - First run: while no user can sign in, `/v1/auth/status` says `setupRequired` and the dashboard shows the setup page. It creates the first user (and the default org, project and status page if bootstrap didn't), then goes to **Connect your app** (`#/connect`: the visible key if there is one, `npm install` and the `init()` line with this collector's origin). `/v1/auth/status` `setup` says what the page asks for:
    - `code` (`THEIRSIDE_BOOTSTRAP_API_KEY` or `THEIRSIDE_ADMIN_TOKEN` set; first run as before 0.3.2): `THEIRSIDE_ADMIN_TOKEN` or a one-time setup code each instance prints to its log at start (stored hashed in `install_meta` as `setup_code:<sha256>`, valid 24 h, all deleted on setup).
    - `link` / `open` (zero-config, `config.zeroConfig`: neither set): each start while setup is required logs `Open <THEIRSIDE_PUBLIC_URL or http://localhost:PORT>/setup?token=… to create the first account`. The token (32 base62) is stored hashed under the same `setup_code:` prefix, with no time limit, and all are deleted on setup. `GET /setup` redirects to `/#/setup/<token>`, so the token travels in the fragment, and the request log serializer redacts `/setup?…`. A request that is loopback at the socket and at `req.ip` and carries no forwarding header (`isLocalRequest`) needs no token (`open`). Docker port mappings are never loopback. A credential-less placeholder admin from older bootstraps (`install_meta.bootstrap_admin_user_id`) is claimed rather than duplicated. The setup user is always an admin (also when it claims the placeholder), regardless of `THEIRSIDE_ADMIN_EMAILS`.
  - Passwords: argon2id (`@node-rs/argon2`, 19 MiB, t=2, p=1), 12–256 characters, no composition rules; unknown emails are verified against a dummy hash so timing doesn't reveal accounts.
  - Sessions (`sessions`): a random 256-bit cookie token (`theirside_session`, `HttpOnly`, `SameSite=Strict`, `Secure` when the dashboard URL is https); only its SHA-256 is stored. They end after `THEIRSIDE_SESSION_MAX_AGE_HOURS` (168) or `THEIRSIDE_SESSION_IDLE_HOURS` (24) idle, on sign-out, and for all devices on "sign out everywhere", a password change (except the current one) or a reset; `last_seen_at` is written at most once a minute.
  - CSRF: writes on a cookie session need `x-csrf-token` = HMAC(per-install secret, session hash), returned by sign-in and `/v1/me`; any `Origin` must be the collector's own (or `THEIRSIDE_PUBLIC_URL`'s) and `Sec-Fetch-Site: cross-site` is refused, also on the public sign-in/setup/link endpoints (login CSRF). Bearer requests carry no ambient credential and need neither.
  - Throttling (`auth_throttle`, shared by replicas): failures (password, 2FA code, step-up password) for one email from one address wait 1 s, 2 s, 4 s… up to 15 min from the 5th, existing email or not, even for the right password, starting over after a success or a day (key `login:<email>|<ip>`, so nobody can delay a user at another address); 30 failures from one address in 15 min block it (passwords, admin token, setup code, unknown link tokens); 3 reset emails per address per hour. Every sign-in purges expired sessions, tokens a day past expiry or use, and counts older than a day that aren't locked (they hold emails and addresses). The address is `req.ip`: `X-Forwarded-For` counts only from proxies `THEIRSIDE_TRUST_PROXY` trusts (by default private and loopback addresses).
  - One-time links (`auth_tokens`, SHA-256 of a 256-bit token, in the URL fragment `#/invite/<token>` so it never reaches logs): invites (7 days, per email, a new invite replaces the older one) and password resets (1 hour, admin-generated or, with SMTP, self-service "forgot password" that answers the same for unknown emails). A reset signs the user out everywhere and lifts its sign-in delays. Emails go through the same SMTP settings as alerts (`modules/mail`); the link is always returned too, with the send error if any.
  - Two-factor sign-in (optional, per user; migration 006): TOTP (RFC 6238, SHA-1, 6 digits, 30 s, ±1 step) set up from the account page in two steps (secret + `otpauth://` URL, then a code proves it), plus 10 single-use recovery codes (16 characters from a 30-letter alphabet, ~78 bits, stored as SHA-256, shown once). With 2FA on, the right password returns `{mfaRequired, mfaToken}` (an `mfa` one-time token, 5 minutes) instead of a session; `POST /v1/auth/login/2fa` takes a code or a recovery code. Each code's step is stored (`totp_last_step`) and only later steps are accepted, so a code works once; wrong codes count like wrong passwords. Turning 2FA off and new recovery codes need the password; another user (or the admin token) can turn a user's 2FA off for a lost phone. Wrong confirmations answer 403 (`wrong_password`), not 401, so the dashboard doesn't take them for an ended session.
  - TOTP secrets are encrypted at rest (`SecretBox`): AES-256-GCM with a key derived by HKDF-SHA256 from `THEIRSIDE_SECRET_KEY`, the user id as associated data, stored as `v1.<key id>.<iv>.<ciphertext>.<tag>`. Without the key 2FA can't be turned on or required; if it is lost, codes can't be checked (sign-in answers 503 `secret_key_missing`) and users sign in with recovery codes or have 2FA turned off by another user. Rotation: set the new key and the old one in `THEIRSIDE_SECRET_KEY_PREVIOUS`; each start re-encrypts secrets under the current key, after which the old key can be removed.
  - "Require 2FA for everyone" (`orgs.require_2fa`, Settings → Users): needs the key and the person switching it on to have 2FA. A password user without 2FA can then only reach `/v1/me` and the 2FA enrolment endpoints (403 `2fa_required` elsewhere), on existing sessions too; they can't turn it off. Admin-token and proxy sign-ins are not asked for codes (the token is break-glass; the identity provider owns MFA for proxy users).
  - Trusted proxy sign-in (opt-in, `modules/auth/proxy-auth.ts`): `THEIRSIDE_AUTH_PROXY=header` takes the email from `THEIRSIDE_AUTH_PROXY_HEADER` (default `X-Forwarded-Email`; oauth2-proxy, Pomerium, Cloudflare Access…), `alb` verifies AWS ALB's `x-amzn-oidc-data` JWT: ES256 with the public key ALB publishes per key id (`https://public-keys.auth.elb.<region>.amazonaws.com/<kid>`, cached; region and partition from `THEIRSIDE_AUTH_PROXY_ALB_ARN`), `signer` must be that ARN, unexpired (60 s leeway), ALB's `=` padding tolerated, `email` and `name` claims. The header is believed only when the TCP peer (never `X-Forwarded-For`) is in `THEIRSIDE_AUTH_PROXY_TRUSTED_IPS` (required; addresses/CIDRs, IPv4-mapped IPv6 unwrapped); from anyone else it is ignored and the request is treated as if it weren't there. Each request is authenticated by the header (no session); writes need the CSRF token (HMAC of `proxy:<user id>`) because the proxy's own cookie is ambient. An unknown email signs in when it has a pending invite (accepted on the spot), or with `THEIRSIDE_AUTH_PROXY_AUTO_CREATE=true` (also creates the default org on an install without bootstrap); otherwise 403 `no_account`. Proxy users (`auth_source = 'proxy'`) have no password and aren't asked for 2FA. Order: Bearer admin token, proxy header, session cookie.
  - Break-glass: `THEIRSIDE_ADMIN_TOKEN` still signs in (`POST /v1/auth/login {token}`, or `Authorization: Bearer` for scripts) as a system user `usr_admin_token` (admin of the first org, never listed, no account settings, not counted as the last admin). Unset it to disable.
  - Step-up for changes to someone else's account (reset link, turning their 2FA off, removal, role): the request carries `stepUp: {password, code}` (code only when the actor has 2FA; a recovery code works), or `{adminToken}` in a session from the admin token; without it 403 `step_up_required` with `needs`, wrong values 403 `wrong_password`/`wrong_code`/`wrong_admin_token`. Failures count like sign-in failures; only a complete step-up clears the count. Bearer requests (the token was just presented) and proxy users (their identity provider authenticates every request) are not asked. With SMTP, the affected user is emailed who did what (a reset link sent to them by email is itself the notice); best effort, a failed email doesn't undo the change; responses say `notified`.
  - Removing a user cascades to their sessions; nobody removes themselves, the last user who can sign in or the last admin.
- Bootstrap (self-hosted, `THEIRSIDE_BOOTSTRAP_API_KEY` set, no org yet): org, project, the key (scopes `ingest` + `read`) and a status page with a random token, so SDKs can send before anyone signs in. No user: the setup page creates the first. Idempotent; on later starts it only ensures the key exists. Zero-config (neither variable set) with no key in the install, revoked ones included: org, project and status page if missing, plus a generated key named "Default key" (`ingest` + `read`), kept readable in `api_keys.visible_key` (migration 017) for admins, never logged. `install_meta.first_run_key` keeps two replicas from both generating one.
- API keys: per project, stored hashed (SHA-256) with a 13-character display prefix (only the zero-config generated key is also readable, for admins, until it is revoked), prefixed (`tsd_live_` + 32 base62), scopes `ingest` and `read`. Lookups are cached 60 s, so revocation takes effect within a minute.
- Entitlements: `entitlements.for(orgId)` returns a typed object (`maxProjects`, `retentionDays`, `networkView`, `slaReports`, `sso`, `rbac`, `auditLog`, `maxOrgs`, `maxStatusPages`, `customStatusDomain`, `whiteLabelStatusPage`, `pagingIntegrations`, `monthlyCallLimit`); the editions table in §2 maps them to features.
  - Self-hosted: defaults to the OSS set (`maxProjects: null`, `retentionDays: null` = use `THEIRSIDE_ROLLUP_RETENTION_DAYS`, `maxOrgs: 1`, `maxStatusPages: 1`, all paid booleans false, `monthlyCallLimit: null`); a licence key (`THEIRSIDE_LICENSE_KEY`, Ed25519-signed JWT verified offline with an embedded public key, no phone-home) upgrades it. Expired licence degrades to OSS, never stops ingest or alerts.
  - Licence format: header `{"alg":"EdDSA","typ":"JWT"}`, payload `{iss:"theirside", sub:<licensee>, plan, iat, exp, ent:{<entitlement fields>}}`. Only known entitlement fields with the right type are applied. One licence covers the whole install.
  - Keys: `PRODUCTION_LICENSE_PUBLIC_KEYS` (`apps/collector/src/modules/entitlements/keys.ts`) is empty until the production signing key exists. A clearly marked dev keypair (`dev-keys.ts`) signs test licences, accepted only with `THEIRSIDE_ALLOW_DEV_LICENSE=1`. Tooling: `pnpm --filter @theirside/collector licence keygen|sign|verify`.
  - Cloud: resolved from the org's plan by a resolver plugged in through `EntitlementsResolver`.
- Usage metering: `usage_daily(org_id, project_id, day, calls_ingested, events_dropped_reported)` updated on ingest. Feeds limits. `monthlyCallLimit` (UTC calendar month, whole org) is enforced only when set: the batch is rejected with 429 + `Retry-After`. Month-to-date usage is re-read at most once a minute per org.

## 5. Data model (Postgres)

### 5.1 Config tables
`orgs`, `users`, `memberships`, `projects`, `api_keys` (`visible_key`, migration 017: only the key a zero-config first start generated; cleared on revoke), `providers` (project, name, host patterns, explicit routes, support email/URL/notes, public display name, `is_public`, `path_privacy` strict/balanced/NULL and `allowed_path_words`, migration 004; `last_call_at`, migration 008: the latest call seen at ingest, moved forward in the ingest transaction at most every 30 s per provider, filled from rollups on upgrade; `endpoint_aliases`, migration 009: merged templates `METHOD /old` → `/new`, rewritten at ingest; `thresholds`, migration 010: per-provider threshold overrides, docs/scoring.md; `webhook_thresholds` and `webhooks_public`, migration 018: the provider's webhook overrides and its status page switch; `expected_statuses`, migration 022: statuses marked expected per endpoint from the dashboard, `METHOD /template` → [400, …], applied when scoring), `alert_channels`, `alert_deliveries`, `status_pages` (project, public token, provider filter, theme), `settings` (per project overrides for incident thresholds), `sdk_instances` (service, environment, sdk version, last seen (any batch), last event (batches with calls), dropped events, serverless, platform), `event_gap_seconds` and `event_batches` (migration 013: a running average of the time between batches with calls, for SDK health), `service_templates` (migration 014: per service, environment, provider, host, method and template, last seen; written at ingest at most every 30 minutes per template and collector; pruned after 7 days; pooled learning), `sdk_processes` (migration 012: one row per SDK process: instance id, start time, first/last seen, last event, SDK and runtime version, platform, serverless; pruned 7 days after last seen), `webhook_sources` (migration 018: per environment, provider and route template: first seen, last delivery and the service that received it, moved forward at ingest at most every 30 s per source and collector; `expected_quiet`; `silence_forced`, migration 020: silence judged although the gap model calls the source irregular), `webhook_candidates` (migration 019, webhook discovery: per project and route template: method, suggested name, status pending/confirmed/ignored, confirmed provider, first/last seen, last service, decided at/by; `notified_at` (migration 023): in a "new webhook route" message; at most 50 pending per project at ingest (`MAX_PENDING_CANDIDATES`), pending ones not seen for 30 days pruned by the retention job; a provider merge moves confirmed names), `webhook_candidate_days` (migration 019: deliveries per route and UTC day, 30 days), `inbound_baselines` (migration 018: normal rejected share, handler p50/p95, lag p95, history, learning, and `silence`: the hour-of-week rates of deliveries and of minutes with a delivery, dispersion, deliveries and hours behind them, the normal gaps' count and longest gap, irregular; `model`, migration 020: the rejections' overdispersion and the slow and late classes), `usage_daily`, `sessions`, `auth_tokens`, `auth_throttle`, `user_recovery_codes` (§4), `install_meta` (per-install key/value: session secret, bootstrap admin id, last run of slotted jobs, future network `contributor_id`). Schema: `apps/collector/migrations/001_init.sql`. Provider rows are created automatically from names seen in traffic (with one seen host); users then fill in support contacts and public display names.

### 5.2 Event tables
- `events`: raw, declaratively partitioned by day of `received_at` (`events_YYYYMMDD`); columns per the shared schema plus `org_id`, `project_id`, `received_at`, `direction` (`outbound`, or `inbound` for webhook deliveries; migration 018) and `sent_at` (inbound: the sender's signed time), `expected` (migration 022: the reason label of a 4xx the app marked expected; such events are never failure samples). Every outgoing reader (request-ID samples, endpoint merges) filters `direction = 'outbound'`. Retention `THEIRSIDE_RAW_RETENTION_DAYS` (default 30); partitions for today and 3 days ahead created by the scheduler (and on demand if an insert finds none), whole days older than retention dropped.
- `rollups_1m`: (org, project, environment, provider, endpoint, method, minute) → total, ok, per-outcome counts (one column per outcome), `status_429`, `status_3xx`, `status_400`, `status_401`, `status_403`, `status_404`, `status_409`, `status_422` (migration 016; behaviour-change detection), `expected` (migration 022: of `ok`, 4xx answers the app marked expected in code; they are counted in `ok`, not in `http_4xx` or the status columns), latency histogram `lat0`…`lat129` (migration 021: one nullable column per bucket of `packages/shared/src/histogram.ts`, NULL when empty; rows from before collector 0.4 keep the coarse columns `h0`…`h17`, NULL in newer rows, and readers spread them over the fine buckets), `latency_sum_ms`. Upserted in the ingest transaction from per-batch in-memory aggregates (one `INSERT … SELECT unnest(…) ON CONFLICT DO UPDATE`; keys sorted to avoid deadlocks). Retention default 90 days (entitlement-capped in cloud). All dashboards, scoring and the status page read rollups, never raw events; raw events are for samples (request IDs, error codes) and debugging.
- `rollups_expected_1m` (migration 022): (org, project, environment, provider, endpoint, method, minute, reason) → calls the app marked expected in code with that reason label (at most 10 reasons per key in one batch, the rest `other`). Upserted with `rollups_1m`, moved with provider and endpoint merges, same retention. Only the endpoint page's per-reason series reads it.
- `rollups_inbound_1m` (migration 018): (org, project, environment, provider, endpoint (our route template), minute) → total, accepted (2xx), rejected (everything else), `status_3xx`, `status_401`, `status_403`, `status_4xx` (other), `status_5xx`, `unanswered` (closed before our answer), handler-duration histogram `dur0`…`dur129` + `duration_sum_ms`, `lag_count`, lag histogram `lag0`…`lag129` (the latency buckets read as seconds) + `lag_sum_s` (migration 021: nullable bucket columns like `lat*`; older rows keep `d0`…`d17` and `l0`…`l17`). Upserted in the ingest transaction; same retention as `rollups_1m`; moved with a provider merge. Webhook scoring, the Webhooks dashboard and the status page's webhooks row read only this.

### 5.3 Incident tables
`incidents` (environment, provider, `direction` (migration 018: `outbound`, or `inbound` for webhook incidents, whose one endpoint is the route with method POST), scope: endpoint or provider, kind: errors, latency, auth, not_found, validation, rate_limited or behaviour (migration 016), or webhook_silence, webhook_rejections, webhook_slow, webhook_lag (inbound), `window_minutes` (migration 015), `deploy_hint` (migration 016), `resolution_note` (migration 022: why it was resolved when not by recovery, a status marked expected; such a resolution starts no cooldown), status, opened/resolved, last alerted rate and p95, last evaluated minute, `alerts_muted`, peak error rate, peak p95, baseline snapshot, summary text, sample request IDs; columns added in `002_incident_alerting.sql`), `incident_endpoints` for grouped provider incidents (first seen, recovered, peak rate per endpoint), `baselines` (cached per endpoint: provider-error rate, 4xx rate, 429 rate, `model` (migration 020: the count tests' overdispersion per failure class and the slow class: threshold, normal share, overdispersion; the normal share of each status marked expected from the dashboard, the safety net's base), `status_mix` (normal share of 401/403, 404, 400/409/422, other 4xx and all unsuccessful calls; migration 016), p50, p95, sample size, history minutes, `learning` flag, computed_at).

### 5.4 Network aggregate format (fixed now, used later)
A row = `rollups_1m` minus tenant identifiers: `host`, `method`, `endpoint`, `minute`, outcome counts, histogram, plus a random per-install `contributor_id`. Only providers matched to the catalog (`source = 'catalog'`, public known providers) may ever be converted; discovered-only domains and configured names never. Self-hosted uplink is opt-in, off by default.

### 5.5 Storage abstraction
Collector code depends on repository interfaces (`EventStore`, `RollupStore`, `IncidentStore`, `ConfigStore`, plus `UsageStore`), bundled as `Storage` with `transaction(fn)` (unit of work: ingest writes raw events, rollups, usage and the SDK heartbeat atomically) and `withLeaderLock(name, fn)` (advisory lock). Postgres implements all of them (`apps/collector/src/storage/`); only that directory contains SQL. Cloud can later move `EventStore`/`RollupStore` to ClickHouse without touching scoring or API code.

## 6. Ingest protocol

- `POST /v1/ingest`, `Authorization: Bearer <project api key>`, `Content-Encoding: gzip`, body `{ protocol: 1, sdk: {name, version}, service, environment, dropped, lastFlushError?, sampleRate?, instance?: {id, startedAt}, runtime?: {name, version?, platform?, serverless?}, stats?: {queued, sent, failedFlushes}, events: [...] }`. `instance`, `runtime` and `stats` (SDK 0.2.0+, optional) identify the process, its runtime and the SDK's counters; an empty `events` array is a heartbeat (an idle long-running process, every 5 minutes; never in serverless mode).
- Event: `{ ts (epoch ms, call start), provider (string, or null for a host found by auto-discovery: the collector assigns the provider), host, method, endpoint, status|null, durationMs, outcome, errorCode?, correlationId?, providerRequestId?, service?, environment?, sdkVersion?, direction?, sentAt? }`. `candidate: true` with `count` marks a webhook-discovery report (inbound only: `provider` is the suggested name or `unknown`, `count` the deliveries since the route's last report); the collector stores it only in `webhook_candidates`/`webhook_candidate_days`, never as an event, rollup or source, and doesn't count it as calls. `direction: 'inbound'` (SDK 0.3.0, collector 0.4.0) is a webhook delivery our app received: `provider` the sender, `host` the literal `inbound`, `endpoint` our route template, `status` our answer (null: unanswered), `durationMs` our handling time, `ts` the receive time, `sentAt` the sender's signed send time. Optional fields: protocol stays 1. An older collector strips `direction` and would store deliveries as calls, so the SDK sends them on `/v1/ingest` only after `GET /v1/sdk-config` answers `inbound: true`; before that an SDK with `inbound: true` sends them, alone, to `POST /v1/ingest/inbound` (collector 0.4.0+, same handler and limits), which an older collector answers with 404. The SDK sends `service`/`environment`/`sdkVersion` once in the header; the collector fills them into each event.
- `sampleRate` (0, 1], default 1: only `ok` events are sampled, so the collector weights `ok` events by `round(1 / sampleRate)`.
- Limits: 1 MB compressed, 16 MB decompressed (gzip-bomb guard), 5,000 events per batch. 413 above that, 429 when over plan limits (SDK backs off), 503 + `Retry-After: 30` when storage is down. Also 401 (missing/invalid/revoked key or no `ingest` scope; checked before the body is read), 400 (invalid JSON or schema), 415 (unknown `Content-Encoding`). Success: `202 {accepted: n}`.
- Unknown fields are ignored; protocol bumps only for breaking changes, and the collector accepts the previous version for at least 6 months. `provider: null` (auto-discovery) stayed protocol 1: collectors with discovery accept both forms; an older collector rejects such batches. The SDK detects it: a 404 on `GET /v1/sdk-config` turns auto-discovery off for that process with one always-on `console.warn`, drops discovered events already queued, and keeps recording listed providers. Upgrade the collector to get discovery.
- Provider assignment at ingest (`modules/discovery/directory.ts`): excluded hosts are dropped; a host already on a provider (exact or pattern) goes there, except that a provider's own fold pattern (`*.domain`, below) never wins over a more specific catalog entry for another provider (a folded `*.googleapis.com` on Google Cloud doesn't take `places.googleapis.com` from Google Maps Platform); else the catalog (`packages/shared/catalog.json`, longest domain match in labels; `*` matches within one label, `email.*.amazonaws.com`, `*-aiplatform.googleapis.com`) or the registrable domain (`tldts`, Public Suffix List incl. private suffixes). Hidden/internal providers drop their events (also for SDKs that send names). Caps: 300 providers per project (then the `Other` provider), 50 hosts per provider, 20 subdomains of the provider's domain fold into `*.domain`. `category = infrastructure` (AWS, Google Cloud, Azure, CDNs…) is created with alerts off: incidents are tracked and shown, muted. The big clouds' end-user APIs have their own entries with alerts on (Google Maps Platform, Gemini and Cloud AI APIs, reCAPTCHA Enterprise, Play Developer API; Amazon SES, Bedrock, AI services, Cognito, End User Messaging, Location Service; Azure OpenAI, AI services, Communication Services, Maps; Cloudflare Turnstile). When a release moves hosts to new catalog entries, `catalogRegroupJob` (`modules/discovery/regroup.ts`, once per install per change, `install_meta` `catalog_regroup:<id>`) re-groups them in existing projects: only hosts the previous catalog placed in the provider they are in, only out of providers nobody edited (no rename, public name, hide/internal, alerts toggle, support contact, path settings, routes or own host patterns). A provider whose hosts all move is merged into the new one with its history; otherwise the hosts move and history stays (rollups have no host column).

## 7. Scoring and incidents

Full rules, formula and defaults: `docs/scoring.md`. Summary:

- Scheduler runs every minute, 5 s past the minute (and once on startup), and evaluates the last complete minute (scheduler jobs in order: partitions, incidents, webhooks (inbound incidents), alerts, discovery digest, template merge, endpoint merge, rollup retention). The digest (hourly), the template merge (03:00 UTC) and the endpoint merge (hourly) record their last completed slot in `install_meta` (`job:<name>:last_slot`) and run whenever the current slot is newer, so a slot missed while the collector was down runs on the first tick after startup (several missed slots run once; a failed run is retried next tick; nothing recorded counts as due).
- Baseline per endpoint from the last 7 days of rollups, excluding the last 15 minutes and incident minutes. `learning` until ≥ 24 h and ≥ 500 calls; while learning the provider-error rate is max(observed, 1%). Cached in `baselines`, refreshed every 10 min.
- Provider errors: `http_5xx`, `timeout`, `conn_reset`, `conn_refused`, `dns`, `tls`. Weighted lightly: `http_4xx`, 429. Ignored: `aborted`.
- Score 0–100 over the last 5 min → green (≥ 90) / amber (≥ 60) / red. Provider score = volume-weighted, at least amber if any endpoint is red.
- Open incident: 3 consecutive minutes with ≥ 20 calls in the 5-min window (low traffic: 15/30/60 min) and ≥ 3 provider errors and provider-error rate ≥ max(5× baseline, baseline + 5 pp) and the count test (≥ 5 errors above the expected count and a beta-binomial p < 0.001 with the endpoint's learned overdispersion); or the calls slower than max(3 × normal p95, normal + 1000 ms) passing the same count test against their normal share and reaching max(normal + 2.5 pp, 5 × normal); or a status group far above its normal share (docs/scoring.md). Group endpoints of one provider (one open incident per provider). Resolve after 10 healthy minutes per endpoint; 30-min cooldown (incidents inside it are recorded but muted). Alerts on open, escalation (rate or p95 doubles for 3 windows, or another endpoint joins), resolve. Thresholds overridable per project (`settings.thresholds`).
- Every alert says whether the provider's other endpoints are healthy and carries a paste-ready summary for the provider's support.
- Expected outcomes (docs/scoring.md "Expected outcomes"): 4xx answers that are normal business answers. Tagged in code (SDK `markExpected`/`expecting`, event field `expected`): counted as successful at ingest, per reason in `rollups_expected_1m`. Marked from the dashboard per endpoint (`providers.expected_statuses`): moved into the successful calls when scoring (`scoring/expected.ts`, in the incident job, baselines, health API and charts), with a safety net: a marked status above max(80%, halfway from its normal share to 100%) for 10 minutes opens a `behaviour` incident. Marking recomputes the endpoint's baselines and resolves an open incident it explains with a note. Alerts of status-class incidents (`auth`, `not_found`, `validation`) carry `markExpectedUrl` (`THEIRSIDE_PUBLIC_URL/#/incidents/<id>/expected`), shown in Slack as a "Mark as expected" button.
- Webhooks (docs/scoring.md "Webhooks"): per source, silence (the gap weighed by the empirical-Bayes hour-of-week rate of minutes with a delivery must be unlikely as one negative-binomial draw (`maxPValue`), longer than 1.5 × the longest normal gap, and at least 15 minutes, with 21 days and 100 deliveries of history; never for expected-quiet routes, irregular sources unless switched on, or when the receiving service stopped reporting; held project-wide while every source is quiet at once), rejections (the error rule on the non-2xx share), slow handling (the latency rule on handler durations) and lag (deliveries later than 3× the normal p95 lag and +60 s, the same way). One open inbound incident per source; silence opens at once and resolves on the next delivery; the others use the open/resolve minutes. Alerts carry `direction: 'inbound'` and a `webhook` block (last delivery, silent minutes, expected per hour, p-value, 401/403 share, lag); Slack and email headers say "Stripe webhooks".
- The incident job recomputes from rollups each tick and is idempotent per minute (`incidents.last_evaluated_minute`); the engine (`incidents/engine.ts`) is a pure function of the open incident and per-endpoint evaluations.

### 7.1 Alert delivery

- Channels (`alert_channels.kind`): `slack` (incoming webhook, Block Kit; config `{webhookUrl}`; endpoint templates and hosts in every message and in the notification fallback are inline code, so `:id:` never becomes an emoji; other text has `&<>` escaped and emoji shortcodes broken with a zero-width space; headers are `plain_text` with emoji off), `email` (SMTP via nodemailer; config `{to: []}`), `webhook` (config `{url, secret}`). Adapters implement `ChannelAdapter` (`alerts/channels.ts`); `ee/` paging integrations plug in the same way.
- Rendering (`alerts/render.ts`, snapshot-tested): Slack = header (event + provider), title, fields (duration, environment, provider support), one line per endpoint (error rate and p95 vs normal; 5 listed, then "…and N more"), the "other endpoints" line, the provider summary in a code block, an "Open in dashboard" button, plus a plain `text` fallback; every text is capped to Slack's limits (header 150, section 3000, field 2000, 10 fields, 50 blocks, fallback 4000). Email = multipart plain text + inline-styled HTML, subject `[Theirside] Acme Cards POST /v2/cards/:id/activate failing 38%` (non-open events prefixed with the event, e.g. `Incident resolved:`).
- SMTP: `THEIRSIDE_SMTP_URL` (`smtp://…:587` STARTTLS, `smtps://…:465` TLS) or `THEIRSIDE_SMTP_HOST` + `_PORT` (587, or 465 when `_SECURE`) + `_USER`/`_PASS`; TLS is required whenever credentials are set (`THEIRSIDE_SMTP_REQUIRE_TLS=false` to allow plain text). Examples for Gmail, SES and Postmark in `.env.example`.
- Links: alerts link to `THEIRSIDE_PUBLIC_URL/#/incidents/<id>`; without `THEIRSIDE_PUBLIC_URL` they carry no link (never a localhost one). Status page URLs, the embed snippet and `embed.js` fall back to the request's origin.
- Failed sends are stored and shown as an actionable message: `HTTP 404 from hooks.slack.com: no_service` (Slack's reason body), `connection failed (ECONNREFUSED): …`, `timed out after 10 s`, `SMTP authentication failed: 535 …`, `SMTP server rejected the sender or recipients: …`.
- Webhook signing: header `x-theirside-signature: t=<unix s>,v1=<hex HMAC-SHA256(secret, "<t>.<body>")>`, plus `x-theirside-event` and `x-theirside-delivery`. Body = the `AlertPayload` JSON (event, title, provider, environment, `kind`, endpoints with current and normal error rate and p95, `otherEndpointsOk`, `otherEndpointsText`, `summary`, dashboard `url` (null without `THEIRSIDE_PUBLIC_URL`), timestamps, `durationMinutes`, provider `support` contact). Fields are only ever added.
- Alerts are queued as `alert_deliveries` in the same transaction as the incident change, sent by the `alerts` job; failed attempts retry after 30 s, 1, 2, 4, 8 min, then `failed`. Every attempt updates the row (`attempts`, `last_error`, `sent_at`).
- Admin API (session or `Bearer THEIRSIDE_ADMIN_TOKEN`; writes need owner/admin): `GET/POST /v1/admin/alert-channels`, `PATCH/DELETE /v1/admin/alert-channels/:id`, `POST /v1/admin/alert-channels/:id/test` (synchronous send, returns the result), `GET /v1/admin/deliveries`. Secrets are write-only (returned redacted).

## 8. Security and privacy

- 2026-11-10: Inbound webhook monitoring (free; design recorded before the code). Per webhook source (environment, provider, route template) the collector detects **silence** (no deliveries for longer than the learned hour-of-week rate allows), **rejections** (our app answering non-2xx, 401/403 named apart), **slow handling** (handler p95) and **delivery lag** (receive time minus the provider's signed send time). Decisions:
  - **Capture** with `diagnostics_channel` `http.server.request.start` / `http.server.response.finish`, present and identical on every supported Node (checked on 18.18.0, 18.20, 20.9, 22, 24), so Express, Fastify and Nest need no middleware. At request start the SDK checks only the *presence* of allowlisted header names (`packages/shared/src/webhooks.ts`, verified against each provider's docs) and the declared `webhooks: [{ path, provider }]` routes; any other request returns before anything else is read, and nothing is ever recorded for it. The only header *value* read is the timestamp (a timestamp header, or the `t=`/`ts=` part of a signature header), turned into a number at once; signatures, bodies and other headers are never read. State between start and finish lives in a `WeakMap` keyed by the response, so an abandoned request can't leak. A connection closed before we answered is recorded with status null and outcome `timeout` (the provider gave up and will retry). Not on the fetch build or in serverless functions, which have no `node:http` server.
  - **Detection by header combination**, never by one shared name: GitHub by `x-github-event` (its `x-hub-signature` is shared with Intercom and Bitbucket), GitLab by `x-gitlab-event` before the generic Standard Webhooks headers. Senders that can't be told apart from headers are named after the mechanism (`Svix` for Clerk, Resend and every Svix customer; `Standard Webhooks`) unless the team declares the route; Adyen and Mailgun sign in the body and need a declared route. Declared routes win over detection. `webhooks: false` turns inbound capture off.
  - **Wire format**: an inbound delivery is a `CallEvent` with `direction: 'inbound'`, the provider set, `host: 'inbound'` and optional `sentAt`. Optional fields only, so protocol stays 1. An older collector would store them as outgoing calls (it strips unknown fields), so the SDK records inbound deliveries only once the remote config says `inbound: true` (collector 0.4.0+); deliveries in the first moment after start, before that config arrives, are not recorded. With `remoteConfig: false` the SDK assumes a current collector.
  - **Storage**: raw events gain `direction` and `sent_at` in the same `events` table. Inbound rollups get their own table, `rollups_inbound_1m` (environment, provider, endpoint, minute: deliveries, accepted, rejected, 3xx/401/403/other 4xx/5xx, closed before an answer, handler-duration histogram, lag histogram), rather than a `direction` column in `rollups_1m`: every existing `rollups_1m` reader (health, scoring, series, merges, status page, demo seed) would need a filter, and one forgotten filter would mix webhooks into provider health. Inbound rows also need lag columns and have no host or method. The lag histogram reuses the 18 latency buckets in **seconds** (1 s … 18 h), because lag is seconds to hours and the millisecond buckets end at 65 s. Rollups stay the only input of scoring, dashboards and the status page.
  - **Config**: `webhook_sources` (one row per source: first seen, last delivery, last receiving service, `expected_quiet`), `providers.webhook_thresholds` (per-provider inbound overrides, separate from the outgoing ones: a low minimum set for a provider's API traffic says nothing about its webhooks), `providers.webhooks_public` (status page, off by default).
  - **Incidents** share the `incidents` table (new `direction` column, kinds `webhook_silence`, `webhook_rejections`, `webhook_slow`, `webhook_lag`) and therefore the incident list and the alert channels, but have their own engine (`incidents/inbound.ts`): silence opens on its p-value at once and resolves on the next delivery, which the outgoing 3-bad / 10-healthy-minute rules can't express. One open inbound incident per source; a stronger kind takes over (silence, rejections, slow, lag). Outgoing incident lookups filter on `direction = 'outbound'`. Inbound incidents don't change a provider's outgoing score or status.
  - **Silence statistics** (`scoring/silence.ts`, docs/scoring.md): hourly delivery counts over `silenceHistoryDays` (28), hours in silence incidents left out. Rate per hour of week as an empirical-Bayes estimate: the slot's mean pulled toward the hour-of-day mean with a strength fitted from how much that hour varies across weekdays (revised while building: fixed pseudo-hour shrinkage toward the overall mean gave a weekday-only source's empty weekend hours enough expected deliveries to page every weekend). Webhook traffic is bursty, so the zero-arrival probability uses a negative binomial, with the dispersion estimated against the hour-of-day profile (deliberately conservative: day-of-week variation counts as noise): P(0 in gap) = Π over the clock hours in the gap of (1 + Λₕ/k)^−k. Open when that is below `maxPValue`, the gap is at least `silenceMinGapMinutes` (15), and the source has `silenceMinHistoryDays` (7) of history and `silenceMinDeliveries` (100) in it, so naturally rare sources never page. Hours aren't independent (a quiet weekend is one event), and even the fitted model gave p ≈ 0.0001 by Sunday evening for a weekday-only source, so silence also needs the same window one to four weeks back to have had a delivery each time (added while building; the check queries only when the model already says silent). Not when the source is marked expected quiet, or when the service that last received it has stopped reporting (SDK health already says so; it is the app, not the provider).
  - **Rejections, slow handling, lag** reuse the outgoing statistics: the same window and low-traffic widening, minimum counts, rate threshold and binomial test (rejections against the source's normal rejected share), and the p95 rule (handler duration against `latencyMultiplier`/`latencyDeltaMs`, lag against `lagMultiplier`/`lagDeltaSeconds`), from inbound baselines (`inbound_baselines`, 7 days, incident minutes excluded, refreshed every 10 minutes).
  - Smaller choices: the expected-quiet switch is a member action like alerts on/off, webhook thresholds and the status page switch are admin-only like their outgoing counterparts; the provider's alerts switch covers its webhooks; cooldown is per kind (rejections right after a silence aren't muted); deliveries count toward `monthlyCallLimit` like calls; Square's only timestamp is the first attempt's, so no lag is computed for it (retries would look like lag); the webhook row on the status page needs the provider public as well; the demo uses Standard Webhooks signing for its fake sender (a spec, not a company) and declares the route to name it NotifyCo.
- 2026-11-10: Inbound webhooks on AWS Lambda and before the remote config answers (SDK 0.3.0, collector 0.4.0). Lambda has no `node:http` server, so `wrap()` reads the invocation event: API Gateway REST/HTTP API, ALB and function URL events have a recognisable shape, everything else is ignored, and `body` is never touched (a test fails if it is read). The recorded status is what the sender got rather than what the handler meant: AWS answers 502 on REST APIs and ALB for a throw or a result without `statusCode` and 500/200 on payload 2.0, and a 502 the sender sees is a real rejection that retries. A cold start can't wait for the remote config without losing the deliveries it handles, so `inbound: true` sends them before support is confirmed. They need a way for an older collector to refuse them, because it strips `direction` and would store them as calls: a separate path, `POST /v1/ingest/inbound`, which older collectors don't have (404). The alternatives were worse: a protocol bump would make every new SDK's batches look breaking, an unknown field is silently stripped, and a deliberately invalid field is a hack. Those batches carry only inbound events, so a 404 never costs outgoing calls. Long-running servers keep the remote-config handshake, but hold the first 500 deliveries for at most 60 s instead of dropping them, because the config normally answers within a second and a restart shouldn't punch a hole into silence statistics; they don't use the probe path, so a server against an old collector never sends a request it will refuse.
- 2026-11-10: Webhook discovery for senders without a known signature header (SDK 0.3.0, collector 0.4.0). The SDK reports POST/PUT routes that look like webhooks as *candidates*, and the collector lists them under Settings → Providers. They are never scored until an admin confirms the route with a name; it then goes to the SDKs in the remote config as a declared route. Members may ignore a route, the same split as expected-quiet (member) versus thresholds (admin), so anyone can clear noise but only an admin turns on paging. Avoiding false positives on ordinary API traffic took several layers. Only POST/PUT. Never with browser headers. `events`, `notify` and `notifications` are ordinary REST nouns, so they count only at the end of the path and without API credentials headers, while `webhook(s)`, `hook(s)` and `callback(s)` count anywhere. Whatever slips through is cleared by a member's ignore. Volume is bounded by aggregation in the SDK: one event per route a minute with a count, and 50 routes per process. The cap of 50 undecided routes per project and 30-day ageing keep a busy `/events` API from filling the table. Candidates get their own tables rather than rows in `rollups_inbound_1m` with a flag, so nothing that scores, alerts or draws webhook charts can see them. The cost is that a confirmed route's history starts at confirmation (its hour-of-week rates need hourly counts, which the day counts don't give). The one exception to strict path privacy is the suggested name: a digit-free plain word right after a final route word (or before it). Without it nearly every unknown sender would show as `unknown` at `/webhooks/:id`, which isn't something a person can confirm. The residual risk (a customer slug in that position) is documented with the workaround (declare the route, or `webhookDiscovery: false`), and capped at 16 names per process.

- 2026-11-11: Detection rules changed after the first detection-bench sweep (582 false alarms, 27 must-catch cells missed or slow; docs/benchmarks.md "Detection"). The bench's noise model stayed as it was; each change is a rule change:
  - **Finer latency buckets.** 130 buckets at 2^(1/8) instead of 18 powers of two, because power-of-two interpolation read a true 3× slowdown as 2.78× and the 3× rule never fired. Stored as one packed `int[]` per histogram (first non-empty bucket, then counts) rather than 130 columns; old rows keep their coarse columns and are read spread evenly over their eight fine buckets, so nothing is migrated and baselines are fully fine after 7 days. Storage, measured on Postgres 16 with lognormal latencies plus rare 10–30 s calls: a rollup row grows from 280 bytes to 300 (5 calls/min, ~15 buckets used), 370 (60/min, ~32), 441 (300/min, ~49) and 543 (3,000/min, ~75): +7% to +94%, about +30–60% for typical endpoints, indexes unchanged. Sums over many rows unnest the arrays and group by bucket: ~3.5 ms for a 7-day baseline, where an aggregate function took 450 ms (its state array is copied on every row), so the migration ships only the per-row `theirside_hist_add`.
  - **Count test for every rate rule** (errors, 4xx groups, behaviour, webhook rejections, slow calls, late deliveries): at least `minExcess` (5, new) failures above the expected count, and a beta-binomial test with an overdispersion ρ learned per class from the baseline history's clock hours (method of moments), instead of a plain binomial with 3 failures in all. Reason: at low volume three everyday 404s in twenty calls passed p < 0.001, and the day's error-rate jitter above the 7-day mean made it worse.
  - **Latency and lag as counts.** "p95 ≥ k × normal p95" became "the calls slower than max(k × normal p95, normal + delta) are far above their normal share": the same settings with the same meaning, but two everyday slow calls in a 20-call window no longer move "the p95". Besides the count test the slow share must reach max(normal + 2.5 pp, min(`rateMultiplier` × normal, halfway)): a uniform k× slowdown makes exactly 5% of calls slower than k × the normal p95, so the error rule's 5 pp floor would hide it, and without a floor a busy endpoint's three or four everyday very slow calls in 1,500 paged by chance (seen in the bench: about one a month on steady webhooks).
  - **Small samples look wider, and share the significance.** A window with fewer than 100 calls also tests the wider low-traffic windows (up to 60 min), so a medium endpoint can collect the calls a 5% effect needs; the k windows tested share `maxPValue` (Bonferroni, maxPValue / k each), so testing more windows doesn't add false alarms. Low-volume incidents resolve later (the widest window tested must clear).
  - **Silence from normal gaps.** The product over clock hours of negative-binomial zero-probabilities treated hours as independent and called a day-long gap between test bursts p ≈ 1e-6; the past-weeks guard was trivially satisfied by multi-hour gaps. Now a gap is weighed in normal time (Σ −ln(1 − p) over its minutes, p from the hour-of-week rate of minutes with a delivery) and must be unlikely as one negative-binomial draw and longer than 1.5 × the longest normal gap in the 28-day history; sources whose longest normal gap weighs ≥ 30 (normally quiet for stretches their own rates call near-impossible: test-driven or batch traffic) are "irregular: silence alerts off", shown on the route with a switch to judge them anyway (`webhook_sources.silence_forced`). Weighing gaps by the rate rather than comparing raw minutes within an hour-of-week class (the first idea) keeps one comparison for the whole week: a gap that starts at 17:55 and runs through the night is short in normal time, where by its start class it would look like a daytime gap of 14 hours and make every daytime gap look normal.
  - **Silence rates without sampling noise.** The hour-of-week shrinkage now subtracts sampling noise from the spread of the slot means and estimates the real spread once over all 24 hours (a ratio of sums), on two levels (hour of day toward the overall mean, slot toward hour of day). Reason: in a source's second week each slot had one sample, and a flat 4/hour source showed slots from 2.3 to 6.6/hour, doubling some gaps' weight and paging.
  - **Bench targets scale with traffic**: max(fixed target, minutes until the fault's calls reach max(`minCalls`, `minExcess` / the fault's effect share) + `openAfterMinutes`), from the run's own arrivals; a fault that never brings that many calls is "not detectable at this volume" (a 15-minute 3× slowdown at 4 calls/min brings ~50 calls, of which ~2.5 slow). This is the expected-value time: a fault whose failures arrive later than average can miss it by a few minutes.

- 2026-11-12: Expected outcomes, for APIs that use error statuses as normal business answers (a consent check answering 400). Two levels:
  - **In code** (recommended): `markExpected(reason)` tags the latest outgoing call that ended in the current async context; `expecting(reason, fn)` tags 4xx answers to the calls `fn` makes. Node finds the context with AsyncLocalStorage: each incoming HTTP request's handler runs in its own frame, entered with `enterWith` from `http.server.request.start` (published synchronously just before `request` is emitted, so the handler and its async work inherit it), and a call keeps the frame current at its *start*, because undici's response events run in whatever context the pooled socket has. Outside a request (queue consumers, cron) nothing is matched and the mark counts as a miss: a process-wide "latest call" would tag the wrong call under concurrency. Fetch runtimes have no AsyncLocalStorage: `expecting()` covers calls started synchronously inside it, `markExpected` does nothing. A mark comes after the app has read the answer, so 4xx answers are held from the periodic flush for the 5 s mark window once the app has used `markExpected` (never before, so other apps see no change); forced flushes send them at once. Only 4xx can be expected, and only the reason label (a validated short string) is sent. Tagged calls are counted in `ok` at ingest rather than in a separate class, so every existing rule, baseline, score and status page treats them as successful with no reader changed; `rollups_1m.expected` and `rollups_expected_1m` keep them visible.
  - **From the dashboard** (coarse): marks per endpoint and status, applied when scoring instead of at ingest, so rollups stay raw, unmarking needs no rewrite and the marked share stays measurable for the **safety net** (a marked status above max(80%, normal + (100% − normal) / 2) for 10 minutes opens a `behaviour` incident: "400 (marked expected) now 95% of calls, normally 10%"). The transform is linear, so it applies to minute rows, sums and differences alike (baselines subtract incident windows from sums). Only the 4xx statuses rollups count one by one (400, 401, 403, 404, 409, 422); 429 stays a rate-limit signal. Marking recomputes the endpoint's baselines at once and resolves an incident it explains with a note; that resolution starts no cooldown, so a safety-net incident right after a mark still alerts.
- 2026-11-12 (later): The expected-outcome safety net's limit is max(80%, normal + (100% − normal) / 2) instead of max(80%, 4 × normal): 4 × normal is 100% or more for any status normally at 25% or more, so a contract change answering 400 to everything could never alert on, say, a consent check that answers 400 to 30% of calls. Halfway to 100% is reachable for every normal share (30% → 80%, 85% → 92.5%) and never below 80%. A limit that close to the normal share needed a guard the first version lacked. At 85% normal, bench runs alerted on everyday drift: a share wandering between 80% and 90% crosses 92.5% by chance. And in the first minutes of a fresh endpoint the unknown normal share was taken as 0. A count test against the mean share didn't help: the 7-day mean (83%) understates an ordinary high hour (90%), and it fired at 92%. So the share must now clear the limit **with confidence**: its 99.9% Wilson lower bound must be above the limit. That asks the right question ("has the status taken over?"), not "is this unusual for the mean?". The limit's halfway margin already absorbs normal drift. The cost is a slower or missed alert at low volume with a high normal share: telling "every call answers 400" from "90% do" takes about 60 calls. The safety net also waits until the status's normal share is learned.
- 2026-11-12: Webhook discovery widened after it missed a real delivery: a POST to a custom route (`/v1/<name>`, no route word) with CloudEvents headers, an `x-hmac-signature-sha-256` header and a `webhook.` host. Debug mode is an environment switch (`THEIRSIDE_DEBUG=inbound`), not an init option, so it can be turned on in a deployed function without a code change; it logs to the app's console only. - 2026-11-12 (SDK 0.4.1): On Lambda, `wrap()` records a webhook delivery when the handler returns, because the status the sender got is the handler's result. Code samples are type-checked in CI (`tools/docs-site`, `pnpm docs:check`) against the SDK's published types: `@theirside/sdk` resolves through the package's own `exports` map, which equals `publishConfig.exports` apart from the inactive source condition, so ESM samples get `index.d.ts` and CommonJS samples `index.d.cts`, as for a real install. Type-checking was chosen over running the samples: it catches the drift that matters (renamed options, changed signatures) in seconds without a collector, and the quick-start commands are already run by the self-host quick start job. The configuration tables are generated rather than written: `init()` options from the JSDoc on `InitOptions` (every option now carries a description and `@default`, which also shows in editors), and collector variables from a list next to `config.ts` that a test keeps equal to what it reads.
- 2026-11-14: The collector verifies its database's TLS certificate against a custom CA (`THEIRSIDE_DATABASE_CA_FILE`, with `sslmode=verify-full`), and the image carries AWS's global RDS CA bundle (`docker/certs/rds-global-bundle.pem` → `/app/certs/`). Before, the RDS advice was `sslmode=no-verify` (encrypted, but anything on the path could pose as the database) or building your own image with the bundle. node-postgres would take the CA from `sslrootcert=` in the URL, but its connection-string TLS settings override an explicit `ssl` option, so a separate setting is parsed here (`pg-connection-string`) and the pool gets the merged result; a CA file with `sslmode=disable` or `no-verify` is refused at start rather than silently ignored. The bundle is kept in the repo instead of downloaded during the image build: offline, reproducible builds, and a change to it shows in review (refresh steps in `docker/certs/README.md`). `docker/database-tls-check.sh` (CI) runs the image against a Postgres with a throwaway CA: verified with the CA, refused without it, refused for a wrong host name and for the RDS bundle, and `no-verify` still connects. A startup check (`databaseTlsStatus`) warns, never blocks: a remote database (anything but localhost, 127.0.0.1, ::1, a Unix socket or a single-label name; private IPs count as remote, because a VPC is still a network others share) whose `sslmode` doesn't verify the certificate gets one WARN line with the fix, and the same text for admins through `GET /v1/admin/system` on Settings → SDK health. `require`, `prefer` and `allow` count as unverified, as in PostgreSQL, although node-postgres currently treats `require` as `verify-full`: asking for `verify-full` explicitly doesn't depend on the driver's interpretation.
